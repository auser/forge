# Forge v0.3 Implementation Prompt

Read `specs/project.md`, `specs/adrs/0001-core-architecture.md`, `README.md`, and the v0.2 summary in `specs/implementation-plan.md` first. v0.2 is complete and green (10 BDD features, 16 scenarios, 61 steps). Implement a real, compiling v0.3 of Forge; do not produce scaffolding or pseudocode. Preserve the v0.2 architecture, CLI, and configuration surface; extend rather than rewrite.

## Objectives

- Replace the single-shot `AgentService::run` with an interactive, multi-turn agent loop: model → tool calls → tool results → model, until completion, error, budget exhaustion, or cancellation.
- Implement the tool set entirely through existing abstractions: file reads/writes/edits and commands go through `ExecutionProvider`; graph queries through `ProjectGraph`; skill activation through `SkillRegistry`. The runtime must still never touch processes or the filesystem outside these traits.
- Make `forge resume` and `POST /v1/runs/:id/input` real continuations: resume re-enters the loop from recorded session events; input delivers a user message to a running or paused run.
- Cancellation must abort the loop mid-turn (not just record an event) for both CLI and server runs.
- Upgrade the event protocol to schema v2: `f64` confidence, monotonic per-run sequence numbers, and a `tool_call` payload shape. Keep reading v1 logs (tolerant reader or explicit migration; do not break existing sessions).
- Add a scripted mock model (an ordered queue of scripted responses, including tool calls) so the full loop is deterministically testable offline.
- Bound server run state (explicit cap + eviction) and document the semantics.

## Required behavior

- Tool calls use a JSON tool protocol compatible with the OpenAI tools schema for `OpenAiCompatibleModel`; the scripted mock speaks the same protocol. Providers without `tools` capability must receive a clear typed error rather than silently degraded behavior.
- Risk classification is mandatory for every tool call: reads are `Safe`, writes/edits and skill scripts are `Risky`, deletions and out-of-project writes are `Destructive`. All four approval modes (`auto`, `prompt`, `prompt-dangerous`, `deny`) must be honored inside the loop, and every approval decision is recorded as an event.
- The loop enforces a configurable `max_turns` budget (default sensible, e.g. 25) and records budget exhaustion as an `error` event.
- Every tool start/completion, file change, approval decision, routing decision, and turn boundary appears in the JSONL event stream with correct run/session IDs and sequence numbers.
- The agent loop seeds model context with graph-aware context selection (`ProjectGraph::context`) when a graph is available; absence of a graph must never block a run.
- CLI `forge run` gains `--max-turns`; `forge resume <id>` continues the recorded run; `forge cancel` aborts in-flight CLI runs. Server `POST /v1/runs/:id/input` delivers input to a paused run and `POST /v1/runs/:id/cancel` aborts mid-loop. SSE streams the new tool/turn events without schema breakage.
- No new mandatory external services; everything above works offline with the scripted mock.
